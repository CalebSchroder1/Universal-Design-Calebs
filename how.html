How to build it

Good news: most of this is plain HTML and CSS you already know. Here’s the short list that fixes the problems audits find again and again.

Five building blocks

Open a topic to read it. Everything works from the keyboard: press Tab to reach a heading, then Enter or Space to open it. In most browsers only one stays open at a time.

Structure: start with semantic HTML

Use each element for what it means. Browsers give you keyboard support, focus, and screen reader roles for free.

  • Landmarks: header, nav, main, footer. Screen reader users jump between them.
  • One h1 per page, then headings in order. Pick levels for structure, not for size.
  • Real lists for lists. Real tables for data.
  • Links go places. Buttons do things.
  • Set lang on html and give every page a unique title.
Color and type: readable first, pretty second
  • Contrast: at least 4.5:1 for normal text, and 3:1 for large text and for UI parts like input borders and meaningful icons.
  • Don’t rely on color alone. Underline links. Pair error colors with words or icons.
  • Relative units: size type in rem so it scales with people’s browser settings.
  • Comfortable text: line height around 1.5, and lines of roughly 45 to 75 characters (max-width: 65ch).
  • Reflow: nothing should need sideways scrolling at 320 CSS pixels wide. That’s what 400% zoom looks like on a laptop.
  • Target size: at least 24 by 24 CSS pixels (WCAG 2.2 AA). Aim for 44 by 44.
Keyboard and focus: if you can’t Tab to it, it’s broken

Plenty of people never touch a mouse. Every control must be reachable and usable with Tab, Shift+Tab, Enter, Space, arrow keys inside widgets, and Esc to close things.

  • Never remove the focus outline without replacing it with something just as visible.
  • Keep the DOM order the same as the visual order.
  • Don’t use tabindex above 0. Use 0 for custom widgets and -1 for focus set by script.
  • Add a skip link so people can jump past the navigation.
  • Never trap focus. People must always be able to leave.

Try it: unplug your mouse and use this page.

Media and forms: give everything a name
  • Images: describe what the image is for, not “image of”. Decorative images get alt="" so screen readers skip them.
  • Video and audio: captions and a transcript. No autoplay with sound.
  • Form fields: every input gets a visible label. A placeholder is not a label because it disappears when you type.
  • Errors: say what went wrong and how to fix it, in text, next to the field.
  • Autofill: use autocomplete so people type less.
Preferences: respect what people told their device

Operating systems and browsers let people say what they need. CSS can listen.

  • prefers-reduced-motion for people who get dizzy or distracted by animation.
  • prefers-color-scheme for light and dark.
  • prefers-contrast and forced-colors for high-contrast modes.
  • Never disable zoom with user-scalable=no, and don’t lock the screen orientation.

This site follows your device. Switch your system to dark mode, or turn on increased contrast, and the page updates right away.

A word on ARIA

ARIA adds extra meaning for assistive technology, but the first rule is: if a native HTML element does the job, use it. A real button beats div role="button" every time, because the real one already handles focus, Enter, and Space.

WebAIM’s 2025 analysis found that home pages using ARIA had more than twice as many detected errors on average as pages without it. That doesn’t mean ARIA causes errors. It does mean it’s easy to use wrongly. Reach for it last, and test it.
